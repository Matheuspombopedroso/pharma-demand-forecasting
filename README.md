# pharma-demand-forecasting

Forecasts how many grams of each raw material (active ingredient) a
compounding pharmacy will consume over the **next 7, 15 and 30 days**, so
purchasing can order ahead instead of reacting to stock-outs.

The project covers leakage-safe feature engineering, walk-forward
validation, distributed hyper-parameter search with **Ray Tune**, experiment
tracking and a **MLflow Model Registry** flow with promotion gating and
rollback.

> **Demo with synthetic data.** All data is generated by a fixed-seed script
> in this repo. No real pharmacy, customer or patient data is used. This is
> not a production system and it makes no clinical decisions. It forecasts
> inventory consumption only.

## The problem

A compounding pharmacy prepares personalised prescriptions from bulk
ingredients. Each ingredient has a supplier lead time, so buying decisions
have to be made days or weeks before the material is used. Ordering too late
stops production. Ordering too much ties up cash and risks expiry. The
question purchasing asks every day is:

> *"How much of each ingredient will we use in the next 7 / 15 / 30 days?"*

Consumption has a weekly rhythm (quiet weekends), slow trends, seasonal
products, promotion-driven bursts and the occasional bulk order. The
synthetic generator reproduces all of these ([part 1](docs/01-data-generation.md)).

## Results (hold-out, measured)

Hold-out = the last 28 forecast origins × 8 ingredients (224 rows per
horizon), never used for tuning. Same rows and same metric code for every
forecaster. Lower is better.

| Horizon | XGBoost WAPE | Seasonal mean 4w | Seasonal naive | Naive |
|---|---|---|---|---|
| 7 days | **0.1063** | 0.1485 | 0.1720 | 0.3770 |
| 15 days | **0.0903** | 0.1259 | 0.1693 | 0.3803 |
| 30 days | **0.0765** | 0.1200 | 0.1704 | 0.3714 |

| Ray Tune, 8 configs × 4 folds × 3 horizons | `tuner.fit()` wall time |
|---|---|
| 1 concurrent trial | 679.7 s |
| 4 concurrent trials (4-core laptop) | 251.3 s (**2.70×**) |

What the numbers say, honestly:

- XGBoost beats the strongest baseline (seasonal mean of the last 4 weeks)
  by 3.6–4.4 WAPE points on every horizon. The data is synthetic, generated
  with exactly the patterns the features were designed for, so real-world
  gains would likely be smaller.
- **Tuning did not help on the hold-out.** Ray Tune (24 configs, ASHA) found
  params with better CV WAPE (0.0904 vs 0.0960), but on the hold-out they
  were worse (0.0960 vs 0.0910). The promotion gate rejected that version and
  the default-params model stayed champion. That is the registry flow doing
  its job.

Hardware (i7-1185G7, 4 cores / 8 threads, 39.7 GB RAM, Windows 11), commands
and raw output: [docs/benchmarks.md](docs/benchmarks.md).

## Architecture

```mermaid
flowchart LR
    G[generate-data<br/>synthetic CSV, seed 42] --> F[features.py<br/>lags, rolling stats,<br/>calendar, promo<br/>past-only]
    G --> B[baselines.py<br/>naive, seasonal naive,<br/>seasonal mean 4w]
    F --> T[(feature table<br/>+ targets<br/>+ baselines)]
    B --> T
    T --> WF[validation.py<br/>walk-forward folds<br/>tuning folds + hold-out]
    WF --> RT[tune.py<br/>Ray Tune + ASHA<br/>1 CPU per trial]
    RT -->|best params| TR[train.py<br/>CV, hold-out vs baselines,<br/>refit on all data]
    WF --> TR
    TR -->|params, metrics,<br/>reports, pyfunc model| ML[(MLflow<br/>SQLite store)]
    RT -->|one nested run<br/>per trial| ML
    ML --> REG[registry.py<br/>@challenger / @champion / @previous<br/>promote gate, rollback]
    REG -->|models:/...@champion| P[predict.py<br/>next 7/15/30-day grams<br/>per ingredient]
```

## How to run

Requires Python 3.11+ (tested on 3.12).

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt -e ".[dev]"

pharma-forecast generate-data            # data/consumption.csv
pharma-forecast train                    # default params -> MLflow run
pharma-forecast register                 # first version becomes @champion
pharma-forecast tune --num-samples 24 --max-concurrent 4   # Ray Tune + train
pharma-forecast register                 # new version -> @challenger
pharma-forecast promote                  # only if hold-out WAPE is lower
pharma-forecast status
pharma-forecast predict --out outputs/forecast.csv
pharma-forecast rollback                 # @champion -> @previous

mlflow ui --backend-store-uri sqlite:///mlflow.db   # http://localhost:5000
```

With `make`: `make pipeline`, `make tune SAMPLES=24`, `make test`, `make lint`.

With Docker: `docker compose up --build` runs the whole pipeline once, then
serves the MLflow UI on port 5000 (see [part 6](docs/06-deployment-and-ci.md)).
The Docker files were **not run** on the development machine, where Docker is
not installed.

## Design decisions and trade-offs

| Decision | Why | Cost |
|---|---|---|
| Target = sum over next H days | that is the purchasing quantity | one model per horizon |
| Direct multi-horizon (3 models) | no error compounding from recursive forecasting | 3× training |
| One global model, scale-normalised | shares weekday/promo patterns across ingredients | distorted inputs right after a spike |
| Training rows need `t + H ≤ cutoff` | stops label leakage through overlapping target windows | fewer training rows near each cutoff |
| Hold-out excluded from tuning | unbiased model-vs-baseline comparison | less data to tune on |
| Ray Tune across trials, 1 CPU each | the parallelism that pays off at this data size | Ray start-up overhead (~30 s here) |
| Ray Train not used | data fits in one process; sharding one fit adds overhead | not demonstrated in this repo |
| MLflow logging from the driver | avoids concurrent SQLite writers | trial logs appear after the search |
| Aliases, not stages | stages are deprecated in MLflow; aliases make rollback a pointer move | custom promote logic |
| Promotion gate on hold-out WAPE | blocks regressions automatically | different data end dates → not strictly comparable windows |
| Features built outside the pyfunc | single source of feature code | callers need this package installed |

## Tests

```bash
pytest        # 19 tests
```

- `test_features.py`: scrambles every value after a cut-off and asserts no
  feature or baseline at/before it changes (no-leakage); target and
  baseline arithmetic.
- `test_validation.py`: training labels end by the cut-off for every horizon,
  folds expand and tile without gaps, hold-out excluded from tuning.
- `test_pipeline.py`: train → register → refused promote → forced promote →
  rollback → predict, asserting aliases at each step (temporary SQLite store).
- `test_tune.py`: a 2-trial Ray Tune search end to end.

CI (GitHub Actions) runs ruff, pytest and a small CLI smoke pipeline on every push.

## Limitations

- Synthetic data only, built with the same patterns the features look for.
  Results on real consumption would differ.
- Point forecasts only. Purchasing would really want quantiles (e.g. P90
  demand over the lead time) for safety stock.
- No supplier lead times, stock levels or order quantities. This forecasts
  demand; it does not recommend purchases.
- Single hold-out window of 28 days; the model-vs-baseline gap has no
  confidence interval.
- The promotion gate compares hold-out metrics that may come from different
  windows (see [part 5](docs/05-model-registry.md)).
- Ray was only run on one machine. Timings are single runs on a laptop with
  other processes running.

## Future work

- Quantile objectives (or conformal intervals) and a reorder-point
  calculation using supplier lead times.
- Known-in-advance covariates (planned promotions, holidays).
- Champion vs challenger evaluated on the same fresh window before promotion
  (shadow mode via `predict --alias challenger`).
- Ray Train `XGBoostTrainer` once the data no longer fits in one process
  (many pharmacies × ingredients), and a multi-node Ray cluster.
- Serve `@champion` behind an HTTP API (e.g. MLflow serving or Ray Serve).
